## A. Backend API & auth — 4 findings

Method: `TestClient` over in-memory SQLite, `ECHOLENS_ENV=staging`,
`allow_guest=True`, one demo product and one real product, with real
admin/reviewer/viewer JWTs. Every claim is a real request/response.

### B1. HIGH — an unauthenticated guest can spend OpenAI credits, unthrottled
`api/app.py:1063-1077` (`/graph`), `:1126-1145` (`/feed/candidates`)

Both are `Depends(current_user)`, so a guest reaches them, and **neither carries
`@limiter.limit`**. Each builds a `_metered_llm(...)` and calls it per request.

Worse, `/feed/candidates` takes `refresh: bool = False` straight from the query
string into `force=refresh`, and `cached_themes` only consults its cache when
`not force`. So `?refresh=true` defeats the cache deliberately, on every hit.

I reproduced this independently after my first attempt gave a false negative:

```
UNAUTHENTICATED guest, realistic corpus, 3 requests each:
  /graph                          codes=[200,200,200]  LLM=['themes.group' ×3]
  /feed/candidates?refresh=true   codes=[200,200,200]  LLM=['themes.group' ×3]
  /feed/candidates                codes=[200,200,200]  LLM=[]        # cache works
```

Every comparable spending route is gated — `/chat` 20/min, `/investigations`
6/min + reviewer, `/findings/{id}/recommend` 10/min + reviewer. These two have
neither.

This also makes the comment at `auth.py:26-32` false: it claims a guest "cannot
reach a single endpoint that spends OpenAI credits".

### B2. MEDIUM — unvalidated `days`/`hours` reach `timedelta()` and escape as 500
`api/app.py:1064`, `:1258`, `:1915`

No `Query(ge=…, le=…)` bound, so a large int overflows and the `OverflowError`
is unhandled — a 500 with a stack trace where 422 is correct. `/graph` and
`/snapshot` are guest-reachable.

```
GET /graph    ?days=1000000000     -> 500
GET /snapshot ?days=1000000000000  -> 500
POST /alerts/digest ?hours=1e12    -> 500
```

### B3. LOW — negative windows accepted, producing incoherent output
`api/app.py:1064`, `:1258`, `:1030`, `:2231`

```
GET /snapshot?days=-100 -> 200 {"window_days":-100,
                                "date_from":"2026-10-25","date_to":"2026-07-17"}
```

`date_from` is *after* `date_to`. Also `/backlog/plan?capacity_days=-50` → 200,
`/portfolio/themes?days=-1&limit=-1` → 200. A confidently wrong answer rather

### B4. LOW (design note) — `_owned` treats a NULL `product_id` as claimable
`api/app.py:556`

`not in (None, product_id)` is a deliberate, documented legacy-row fallback, and
`init_db`'s backfill exists to eliminate those rows. But that backfill is caught
and logged rather than fatal (`session.py:78`) — so if it ever fails, NULL rows
become cross-product reachable. Not counted as a finding since it requires a
prior failure.

## P. Agent pipeline & data integrity — 19 findings

The recurring theme: **several comments claim a fix the code does not deliver**,
which is worse than an unfixed bug because it stops anyone looking again.

### P1. CRITICAL — a dead collector is recorded as a confirmed fix
`fixwatch.py:74-86` and `:45-71`

`_rate()`'s docstring says it "returns None rather than 0.0 for an empty
window… collapsing them into 0.0 is what let a stalled collector read as a
verified fix." But `complaint_series()` pre-fills every calendar day with `0`, so
`series` is **never** empty and `_rate` never returns `None`. The exact failure
the docstring claims to have fixed is live.

I verified this independently against an empty corpus:

```
  window  0d -> len(series)= 1  _rate=0.0
  window  7d -> len(series)= 8  _rate=0.0
  window 14d -> len(series)=15  _rate=0.0
VERDICT: always 0.0, never None
```

End-to-end with baseline 5.0/day and zero post-fix rows:
`{'status': 'confirmed', 'baseline_rate': 5.0, 'post_rate': 0.0}`.

Why it matters: `_confirm()` calls `brain.rebuild()`, and confirmed fixes are
mined as validated cause→fix pairs that **seed future investigations as proven
priors** (`graph.py:801-839`). A source outage silently manufactures ground
truth. The same defect stops `check_regressions` distinguishing "no regression"
from "no data".

### P2. CRITICAL (latent) — GitHub `ext_id` truncation collapses issues into one row
`collectors/github.py:130-133`

`f"{repo}#{number}"[:64]` truncates the *number*, not the repo.

```
repo len 74:  #1, #1234, #5678, #9999 -> 1 distinct ext_id (should be 4)
```

I measured the threshold: it starts colliding at **repo length ≥ 62**.
**Your configured repo is `Adityabeecha/Issues`, 21 chars — safe.** So this is
latent for you, and only bites on long org/repo names. Every issue after the
first would be dropped as a duplicate, and `_ingest_issue`'s existing-row branch
would overwrite the first issue's state and labels with each subsequent one.

### P3. HIGH — token budgets exceeded by up to 5.4×
`investigator/graph.py:165, 374, 676`

The `_plan` pre-flight is the *only* budget check before an LLM call. `_update`
(line 374) is unguarded — and its prompt is the largest in the loop, carrying the
full serialized tool result. The first `_draft_finding` attempt (676) is
deliberately exempt.

Real `Investigator.run()` on tier `quick` (cap 50,000 tokens):

```
per-call 20k+20k -> tokens 120000 / 50000  (2.40x)
per-call 45k+45k -> tokens 270000 / 50000  (5.40x)
```

The comment at `:160-164` claims "the ceiling is enforced rather than recorded".
It is enforced only at the plan boundary, so overshoot is bounded by one full
iteration — which is unbounded in tokens.

### P4. HIGH — the claim-grounding guard is bypassable by punctuation
`investigator/guards.py:30` and `:19-23`

`SENTENCE_SPLIT` breaks only on `.!?`+whitespace or newline, so any clause joined
by `;` `,` or `:` inherits the citation from the front of the sentence.
Separately `CAUSAL_MARKERS` misses several natural ways to state a cause. All of
these publish **unblocked**:

```
PASSES  Sync is broken [ev_001]; the crash was caused by the v3.2 release.
PASSES  Root observation [ev_001]: the drop is due to the new SDK.
PASSES  The v3.2 release is the reason ratings collapsed.
PASSES  The spike stems from the new login flow.
PASSES  The spike is attributable to the new SDK.
```

`tests/test_guards.py:70-79` only covers the simple `.`-terminated case — **a
test weaker than the docstring claim.**

### P5. HIGH — `detect_issue_velocity` publishes declining rates as surges
`detector/detect.py:384-416`

Unlike every other detector (`:226`, `:314`, `:354`), this one applies **no
z-threshold**. Its only filter is `recent_count < 2`. It then forces
`severity=_severity(max(z, SEV2_Z))` → SEV2, and `scan()`'s noise gate exempts
SEV1/SEV2 from the z check.

```
issue velocity z: -0.90  recent_count: 2 -> emitted
severity forced to: SEV2      noise gate keeps it? True
```

A *falling* issue rate is published as an "issue_velocity_surge", and
`_severity_priority` uses `abs(z)`, so it then competes for the daily budget.
`tests/test_detector.py:29` asserts only that *a* candidate exists.

### P6. HIGH — App Store cross-product `ext_id` collision discards a second product's reviews
`collectors/app_store.py:84-91`

The dedupe query is `Review.ext_id == ext_id` with **no product filter**, and the
id-less fallback hashes review *text only*.

```
ProductA inserted: 1   ProductB inserted: 0 (skipped as dup)
=> ProductB's corpus has 0 rows
```

`github.py:93-94` correctly scopes its lookup by product; this one does not.
Against the v8.0 scoping guarantee, a product can be starved of its own data.

### P7. HIGH — the collector watermark advances past a failed item, losing it forever
`collectors/base.py:82-103`

The per-item `try/except` `continue`s, but `newest` is still advanced by later
items in the same page. A poison item mid-page is skipped permanently, and the
run reports healthy.

```
run1: 3 fetched, 2 inserted, 1 failed, watermark advanced past it
=> item 2 permanently lost; status: healthy
```

### P8. HIGH — theme labels are attached to the wrong clusters
`themes/discover.py:487-505`

`raw_by_index` is keyed by pre-sort position, then `prepared.sort(...)` reorders
`prepared` without reordering `raw_by_index`. Whenever the LLM returns groups in
any order other than descending size:

```
cluster of 4 ([2,3,4,5]) gets label 'Login fails on Android 14'
cluster of 2 ([0,1])     gets label 'Battery drains overnight'
```

The verbatims shown as evidence come from a **different complaint** than the
statement above them. Directly contradicts the module docstring: "It never
invents a theme. Every label is checked against the words that actually appear in
its cluster."

### P9. MEDIUM — the off-by-one the docstring says was fixed is still present
`detector/detect.py:156-173`

Docstring says the range is "(start, end] — start-exclusive". Pre-fill starts at
`start.date()+1` but the row filter is `if start.date() <= day`, so a row landing
exactly on the boundary creates a 36th bucket and a 29-day "trailing 28d
baseline". The baseline length depends on whether a review happened to land on
the boundary day.

### P10. MEDIUM — near-zero variance produces false SEV1s
`detector/detect.py:196-197`

The zero-variance branch is capped at 4.0, but the `std_b > 0` branch has no
minimum-variance floor. A baseline of 27 days at 5 and one at 6 (stdev 0.19)
with a recent mean of 6 — one extra review per day — gives **z = 5.1, SEV1**.
*Almost*-flat baselines are treated as stronger evidence than perfectly flat ones.

### P11. MEDIUM — a paused case is auto-resumed on the next restart
`investigator/recover.py:20-21`, `graph.py:858-861`

`run()` writes `status = "running"` while leaving `paused=True`, and
`find_interrupted` selects on `status == "running"` only.

```
paused case picked up by find_interrupted: [(1, 'running', True)]
```

A reviewer's deliberate hold is overridden by the next deploy, and the budget
continues to burn.

### P12. MEDIUM — short identical cross-posts satisfy the two-source rule
`investigator/guards.py:104-106`

`MIN_CROSS_POST_WORDS = 5` appends short snippets to `distinct` with no duplicate
check at all — including *exact* matches.

```
identical <5-word cross-post ("battery drains fast") -> True   (should be False)
identical 6-word cross-post                          -> False  (correct)
```

One person posting the same four words twice unlocks `resolved` at ≥0.80. Also
`e["source"]` is compared with exact string equality, so `"github"` vs `"GitHub"`
counts as two independent sources.

### P13. MEDIUM — `COLLECTOR_TIMEOUT_S` is documented but never used
`collectors/registry.py:69-72`

The comment states each collector "gets its own wall-clock ceiling". `grep`
returns exactly one hit: the definition. `run_all` has no timeout, so a hung
HTTP call blocks every later collector indefinitely.

### P14. LOW — a run with failed items is marked `status="healthy"`
`collectors/base.py:105-107` — `source_health` computes `errored = status ==
"error"`, so a collector dropping items on every run reports as non-stale. The
"stale source disclosure" in findings won't disclose it.

### P15. LOW — two inconsistent evidence bars for steering the agent
`calibration.py:100` vs `:146-150` — `overconfident` is correctly gated at
`n >= 20` with a comment explaining why n=8 was wrong. `weak_spots` immediately
below has **no gate**: a single challenge produces a `KNOWN WEAK SPOT` line
injected into every future prompt for that product.

### P16. LOW — unparseable timestamps default to `now()`
`collectors/github.py:106`, `app_store.py:100`, `play_store.py:74` — a malformed
date is stamped with collection time, then read by the detector's windows and by
`reference_now()`, which takes `max(Review.created_at)` as "today". A backfill of
bad-dated rows moves the agent's notion of the present.

## U. UI appearance & accessibility — 14 findings

Method: `npm run build`, built CSS mounted in jsdom, `getComputedStyle` read on
real nodes. Sizes are arithmetic from declared token values.

### U1. CRITICAL — nested interactive controls
`screens/Portfolio.tsx:148` (outer `div role="button"`), `:192` (inner `<button>`)

`role="button"` carries a presentational-children requirement, so assistive tech
may drop the inner button from the accessibility tree, and the row's accessible
name becomes everything inside it concatenated — product name, DEMO badge, band,
"12% negative", headline, up to three reason chips, "#41 summary…". Two tab stops
on one visual target. The inner button does call `stopPropagation()`, so the
intent is right; the structure cannot express it.

### U2. CRITICAL — seven replay controls unreachable by keyboard
`screens/case/TraceTab.tsx:91, 98, 102 (×3), 105, 110`

Replay, play/pause, three speed buttons, exit and FOLLOW are all `<div onClick>`
with `className="el-btn"` — no `role`, no `tabIndex`, no `onKeyDown`. They also
get no focus ring, because `tokens.css:194` targets `[role="button"]` and
`[tabindex]` and these match neither. jsdom confirms `.el-btn` on a `<div>` still
yields `display:inline-flex` — the styling lands, the semantics do not.

`:105` already carries `aria-label="Exit replay"`, so someone considered the
screen reader and still left it unfocusable.

### U3. HIGH — the 720px breakpoint removes sign-out and five screens
`tokens.css:532`

```css
.el-shell nav[aria-label=Main] > *:not(.el-nav-primary) { display: none }
```

Only `.el-nav-primary` survives. On a phone that leaves Today, Cases and Ask —
and **no way to sign out, switch product, or reach Settings, Sources, Patterns,
Calibration or Costs.** Five of twelve screens unreachable.

Folding the logo and spacer is clearly intended; sign-out and the System group
folding with them reads as collateral damage. The System wrapper
(`Sidebar.tsx:269`) is a plain `<div>` never given a class to opt out, unlike
`.el-nav-wide`, which exists for exactly this purpose at 1024px.

**This is the one UI finding that affects every user, not only keyboard and
screen-reader users.**

### U4. HIGH — three onboarding inputs have no accessible name
`screens/Onboarding.tsx:188, 192, 196` via `Field` at `:223`

Also unlabeled: `Chat.tsx:95`, `Brain.tsx:227`, `case/FindingTab.tsx:422`,

### U5. HIGH — touch targets 20–31px; several fail WCAG 2.2 AA
`tokens.css:271-357`

## F. Frontend logic & state — 9 findings

Method: built `dist/`, mounted the real bundle in jsdom with a stubbed
`window.fetch` and seeded `localStorage`, and drove the actual DOM.

### F1. HIGH — Settings saves budget limits to the wrong scope, and says it worked
`api.ts:823` (write, unscoped) vs `:820` (read, scoped) · `screens/Settings.tsx:29,149`

`LimitsPanel` **reads** via `costsSummary()`, which is `scoped()` — the backend's
`_limits(session, pid)` layers per-product overrides on top ("v8.0 — each
product keeps its own budgets"). It **writes** via `setLimits`, which sends no
`product_id`, and `PUT /settings/limits` only ever writes the workspace row.

On any product with a `limits_json` override, the write lands in a row the read
ignores. I reproduced this against the real `_limits` resolver:

```
product override: daily_investigations = 5
effective BEFORE save : 5
workspace row now     : 6      <- the save did land, in the wrong row
effective AFTER save  : 5      <- admin asked for 6, still sees 5
```

The screen is titled "Budgets, limits and **this product**". The admin gets a
green "Limit saved." toast and the number silently reverts. Same bug class as the
already-fixed `setLimits`-via-raw-`fetch` issue: the transport was fixed, the
scope was not.

### F2. HIGH — connecting a source or importing a CSV ignores the active product
`screens/Sources.tsx:187`, `:237` · `api.ts:783-802`

Both forms default their product field to `""` and both API methods are
unscoped. Backend behaviour with a blank product:

- `add_source` uses `product or identifier`, so the source attaches to a product
  named after the **raw package name**, not the one whose screen you are on.
- `import_reviews_csv` writes `Review(product=None)`, so imported reviews land
  attached to **no product** and are invisible to every scoped screen.

This is on a per-product screen subtitled "Where **this product's** feedback
comes from". Nothing errors; the data just never appears. `importReviews` also
bypasses `handle()` via a raw `fetch`, so a 401 here does not bounce to login.

### F3. MEDIUM — a failed `GET /auth/me` falls back to the untrusted localStorage role
`App.tsx:75-78`

The `.catch(() => {})` restores exactly what the comment above it says was
removed ("The server is the only authority on this"). Same seeded storage, only
`/auth/me` differs:

```
A: /auth/me says viewer  -> role=viewer, 'Add a product' hidden   correct
B: /auth/me FAILS (500)  -> role=admin,  'Add a product' SHOWN    stale wins
```

Case B renders the full admin UI for a guest holding a planted or stale
`echolens_role`. Server-side authz still 403s, so this is UI-level only — but a
cold backend is enough to trigger it, and it is the exact failure path the fix
was written for.

### F4. MEDIUM — Today's score strip joins portfolio data by product **name**
`screens/Today.tsx:53`

`PortfolioProduct` carries `product_id`, but the code matches the name string,
and `product` is itself a fallback chain. Any divergence between `/products`'
name and `/portfolio`'s name drops the match, and `ScoreStrip` does
`if (!me) return null` — so the headline number and verdict, the most prominent
object on the home screen, **vanish with no error and no empty state**.

## I. Infrastructure — checked directly

### I1. MEDIUM — every visitor shares one rate-limit bucket in production
`backend/Dockerfile:22`

The limiter keys on client IP via `get_remote_address`. Behind Northflank's load
balancer every request arrives from the proxy, and uvicorn is started **without**
`--proxy-headers`:

```
direct client 1.2.3.4       -> 1.2.3.4
behind proxy, XFF 9.9.9.9   -> 10.0.0.1      # the proxy, not the visitor
with ProxyHeadersMiddleware -> 9.9.9.9       # correct
```

On a public demo a handful of visitors throttle each other out. This compounds
B1: the rate limits that *do* exist are also mis-keyed.

Caveat if fixed — `--forwarded-allow-ips` must only trust the proxy, since a
directly-reachable port would let a client spoof `X-Forwarded-For`.

`verify_password` can never match — correct by design, but the automation
